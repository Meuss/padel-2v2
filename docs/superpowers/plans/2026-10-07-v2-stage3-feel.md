# V2 Stage 3 (Feel) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make hitting the ball feel good and skilful. That covers Drive, Lob and an automatic Smash, Timing (early, perfect, late) that changes power and accuracy, an aimed Serve with a toss and real timing-based Faults, lag-compensated hit judging, Bots that use every Shot, readable hit feedback (Timing arc, ball trail, impact flash, ground marker), and a full synthesized sound set.

**Architecture:** All shot maths is pure and shared, in `packages/shared/src/shots.ts`, and unit tested. The server stays authoritative.
- It keeps a short ball history and judges each swing against the ball state the client was actually seeing (rewind ≤ 250 ms). It then applies the shot velocity to the live ball.
- Shot and contact events ride on snapshots, so the client can animate, flash and play sound in sync with the ball.
- The client adds a feedback module and a Web Audio engine. Sound is synthesized, so no audio files are downloaded or licensed.

**Tech Stack:** TypeScript, the Rapier 0.18.0 server physics (pinned; don't touch), three.js 0.186 for the client, the Web Audio API, and Vitest.

**Spec:** `docs/superpowers/specs/2026-10-07-v2-redesign.md` (stage 3). Glossary: `CONTEXT.md` (Shot, Drive, Lob, Smash, Timing, Serve, Fault, Score call).

## Global Constraints

- The gate: `pnpm typecheck && pnpm test && pnpm build`. Bump `PROTOCOL_VERSION` to **3** in the first task that changes the wire format.
- `stepPlayer()` stays the only movement integrator. Do not change movement, the input queue or ack semantics, except in Task 7.
- Faults always come from what happened on court, never from chance. **Remove** the random serve faults from `match.ts`. Randomness is allowed only in Bot decision-making, through a seeded PRNG.
- Gameplay tuning goes in `packages/shared/src/constants.ts` (the `SHOT`, `TOSS` and `LAG` tables below). There are no magic numbers in server or client code.
- Glossary terms go in code and copy: Drive, Lob, Smash, Serve, Timing ("early" | "perfect" | "late"), Fault, Azul and Rojo.
- Use the existing headless test pattern (`Room.create()`, `room.step()`, `fakeClient` from `packages/server/test/fakes.ts`). Physics runs in tests.
- Verify visual and audio feedback with `pnpm shoot` (dev server running), and use the existing dev auto-join `?join=<name>&bots=3`.
- Sound must never start before a user gesture (browser autoplay rules), and **M** toggles mute (remembered in `localStorage`, wrapped in try/catch).

## Review Focus

- **A swing that arrives with a huge or garbage view time** (an old client, clock skew, a hostile client): the rewind is clamped to `[0, LAG.maxRewindMs]`, there's no crash, and the swing can't hit a ball that has since been hit by someone else (Task 3 test).
- **Serve toss expires with no click:** a Fault ("Missed the toss"), with the second serve or double fault as usual. Bots never miss the toss (Task 2 test).
- **A swing during warm-up:** it still works for knocking about, with drive and lob both applying, and it never ends a point (Task 3 test).
- **An ends swap between toss start and strike:** the target box is computed from the server's side at strike time. Strike is in the same point, so the side can't change mid-toss, but assert that toss state resets on `setupServe` (Task 2 test).
- **Audio when the tab is hidden or before any click:** no errors in the console, no burst of queued sounds when the tab returns, and contact sounds are dropped if they are more than 200 ms old (Task 6 test of the pure scheduling helper).

```ts
// constants.ts
export const SHOT = {
  /** Ball height (m) at contact above which a swing becomes a Smash. */
  smashHeight: 2.1,
  /** |time to closest approach| (s) within which Timing is "perfect". */
  perfectWindowS: 0.08,
  drive: { power: 12.5, lift: 3.6 },
  lob:   { power: 7.0,  lift: 9.5 },
  smash: { power: 16.0, lift: -1.5 },
  /** Multipliers applied for early/late Timing. */
  offTiming: { power: 0.82, lift: 0.9, aimErrorDeg: 9 },
} as const;
export const TOSS = {
  vy: 3.2,            // m/s upward from SERVE.height
  expireS: 0.75,      // toss falls back below the hand → "Missed the toss"
  perfectWindowS: 0.1,// |t - apex| for a clean serve
  depthPerSecond: 14, // metres of depth error per second beyond the window (late → long, early → short)
} as const;
export const LAG = { maxRewindMs: 250, historyMs: 600 } as const;

// shots.ts
export type ShotKind = "drive" | "lob" | "smash" | "serve";
export type Timing = "early" | "perfect" | "late";
/** Signed time (s) until the ball is closest to the racket point; >0 = still approaching. Pure. */
export function timeToClosest(rel: Vec3, vel: Vec3): number;
/** Timing from time-to-closest. */
export function judgeTiming(tClosest: number): Timing;
/** Which shot a swing becomes: smash if the ball is high enough, else the requested kind. */
export function resolveKind(requested: "drive" | "lob", ballHeight: number): "drive" | "lob" | "smash";
/**
 * Ball velocity for a shot. `aim` is a unit world-space XZ direction; early Timing rotates aim
 * by -aimErrorDeg, late by +aimErrorDeg (around +Y), and both scale power/lift by offTiming.
 */
export function shotVelocity(kind: "drive" | "lob" | "smash", timing: Timing, aim: Vec2): Vec3;
/** Toss height above SERVE.height at t seconds after the toss starts (kinematic). */
export function tossOffset(t: number): number;
/** Seconds from toss start to apex. */
export function tossApex(): number;
/** Serve Timing from strike time t (s after toss start). */
export function serveTiming(t: number): Timing;
/**
 * Where a struck serve should land. `box` is the target service box in world coords
 * ({ xMin, xMax, zMin, zMax }, zMin/zMax ordered so |z| grows from the net toward the
 * back). The aim point is clamped 0.4 m inside the box for a perfect serve; for early/late
 * the depth (|z|) is shifted by depthPerSecond × (|t - apex| - perfectWindowS): shorter
 * if early, longer if late. x keeps the clamped aim.
 */
export function serveTarget(aimPoint: Vec2, box: ServiceBox, t: number): Vec2;
export interface ServiceBox { xMin: number; xMax: number; zNear: number; zFar: number } // zNear: |z| near the net, zFar: |z| at the service line, sign carried by `side`
```

Read `serveTarget`'s box as `{ xMin, xMax, zNear, zFar, side }`, where `zNear` and `zFar` are positive distances from the net and `side` (±1) gives the z sign. Define it exactly like this:

```ts
export interface ServiceBox { xMin: number; xMax: number; zNear: number; zFar: number; side: -1 | 1 }
```

- On success, push a `ShotEvent`, with `pos` being the live ball position.
- Served balls push a `ShotEvent` with kind `"serve"` and the serve timing from Task 2.
- Warm-up swings work too: no legality check, but an event is still emitted.

**Rules:**
- A bot swings when its `timeToClosest` for the ball is within `±SHOT.perfectWindowS`. This replaces "in reach once", while keeping the arming logic so a bot never double-hits.

- Shot choice:
  - Smash happens automatically through `resolveKind` when the ball is high.

  - Otherwise Drive.
- Aim: the opposite half, toward the open side, i.e. away from the nearest opponent's x, clamped to ±3.5.
- Bot swings go through the same `resolveSwings` path, with `view = now` (no rewind).

**Interfaces:**

```ts
export function timingArcColor(t: Timing): string;           // pure
export function trailOpacity(ageS: number, kind: ShotKind): number; // pure: 1 → 0 over 0.35 s (smash 0.5 s)
export class Feedback {
  constructor(scene: THREE.Scene, quality: Quality);
  shot(e: ShotEvent, hitterPos: { x: number; z: number }): void; // flash + trail boost + timing arc + smash shake request
  contact(e: ContactEvent): void;                                // small dust puff on floor, ripple decal on glass
  setBall(x: number, y: number, z: number): void;                // trail sampling + ground marker
  update(dtSec: number): { shake: number };                      // returns camera shake amplitude (m) for this frame
  setQuality(q: Quality): void;
}
```

- **Timing arc:** a flat ring segment (`RingGeometry`, 140° arc, radius 0.7–0.85) on the ground under the hitter.
  - It is coloured by Timing and fades over 0.6 s.
  - It carries a small "PERFECT", "EARLY" or "LATE" label drawn in a `Sprite` with a `CanvasTexture`, in bold condensed sans.
  - It is shown for **every** player's shot, so spectators learn the system too.
- **Ball trail:** the last 14 ball positions as a tapered ribbon (`BufferGeometry` updated in place, no per-frame allocation). It is optic yellow with additive blending, and brighter and longer for a 0.4 s window after a smash.
- **Impact flash:** a sprite burst of 0.12 s at the contact point.
- **Ground marker:** a soft dark disc under the ball whose radius and opacity scale with height. It is visible on "low" quality, where shadows are cheaper, and on "high".
- **Smash shake:** 0.06 m of camera shake decaying over 0.25 s. It is applied in `CameraRig` as an additive offset, so add `CameraRig.addShake(amplitude)`.
- **Budget:** the stage 2 budget still applies (≤ 180 calls, ≤ 450k triangles). Pool and reuse every mesh, and allocate nothing per frame.
